# 第二轮检查答辩问答

> 本文档按第一轮检查（10 月 28 日）教师反馈与第二轮整改逐题整理，用于第二轮现场答辩。

---

## Q1：第一轮老师指出“ER 图用于在数据表设计前表达实体、属性及关系，应只保留核心实体和必要扩展”，我们是如何修改的？

**答：**
第二轮对 E-R 图做了彻底重构，将第一轮混杂了物理中间表与技术支撑表的 **14 个实体**收敛为 **6 个核心业务实体**（配套图纸见 [ER图.png](./ER图.png)、说明见 [05_ER图实体说明.adoc](./05_ER图实体说明.adoc)）：

1. **删减非核心与超范围实体**
   - **移出技术支撑表**：将第一轮画入 ER 图的审计日志（`iam_audit_log`）、权限变更记录（`iam_permission_change_log`）和令牌（`iam_token`）全部移出核心 ER 图（物理库中审计与变更日志合并为统一技术表 `iam_log`，令牌落入 `iam_token`）。
   - **移出 RBAC2 约束**：将角色互斥（`iam_role_exclusion`）移出核心 ER 图，仅保留在物理脚本扩展中。
   - **彻底移除通用数据权限**：按“本轮只做功能权限”的要求，删除 `iam_role_data_scope` 和 `iam_data_scope` 两个实体，并同步从数据库和代码中移除数据权限相关实现。

2. **多对多中间表改回标准“联系”，不再画成独立实体**
   - 第一轮将 `iam_user_role`（用户—角色）和 `iam_role_function`（角色—功能）画成了独立实体框。
   - 第二轮按标准 E-R 规范改用菱形联系符号表达：`用户 — M:N — 角色`（分配，对应 `iam_user_role`）和 `角色 — M:N — 权限`（授权，对应 `iam_role_permission`）。

3. **恢复标准 RBAC 命名，并拆分“前端权限”与“后端 API”**
   - 删去第一轮非标准的 `iam_module`（功能模块）和 `iam_function_point`（把前端按钮与后端路径混在一起的功能点）。
   - 恢复标准名称 **用户（`iam_user`）**、**角色（`iam_role`）**、**权限（`iam_permission`）**；将 `iam_permission` 建模为自关联的菜单/按钮树（`MENU / BUTTON`），并独立拆出 **后端 API（`iam_api`）** 实体，建立 `iam_permission 1:N iam_api` 映射，解决一个按钮调用多个接口与防止绕过前端鉴权的问题。

4. **只保留两个必要业务扩展实体**
   - **多系统（`iam_system`）**：支撑多业务系统接入，界定前端权限（1:N）和后端 API（1:N）的系统归属。
   - **分层组织部门（`iam_org`）**：通过 `parent_id` 自关联与 `ancestors` 路径表达多级组织，支撑部门级用户管理范围；不给用户或角色写死管理员标志字段，管理员能力完全来自角色权限。

**改动对比速记：**

| 维度 | 第一轮（10月26日） | 第二轮（当前） |
| --- | --- | --- |
| 实体数量 | 14 个（业务实体与物理/运维表混杂） | 6 个核心业务实体（`iam_system`、`iam_permission`、`iam_api`、`iam_role`、`iam_user`、`iam_org`） |
| 多对多关系 | 中间表画成实体框 | 改为标准菱形联系（`iam_user_role`、`iam_role_permission`） |
| 权限与 API | `iam_module` + `iam_function_point` 混模 | `iam_permission`（前端树）`1:N` `iam_api`（后端接口） |
| 数据权限 / 审计 / 互斥 / 令牌 | 全部画在 ER 图中 | 全部移出核心 ER 图（数据权限彻底删除，其余仅落物理表） |
